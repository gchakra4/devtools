Sampurnayogam AI Gateway System

Production-grade Administrator & Technical Manual for Role-Based AI Orchestration, Multimodal Generation, Database Routing, and Dual Deployments (NAS + Supabase).

Target Audience: System Administrators & Engineers
Runtime: Deno / TypeScript
Database: PostgreSQL (Supabase)
Verified Against Codebase (August 2026)

01 What is the AI Gateway?

The AI Gateway is a specialized, lightweight middleware service that sits between our automation orchestrator (n8n), frontend applications, and external Artificial Intelligence providers (such as Google Gemini, Alibaba DashScope, and OpenAI-compatible vendors).

The Fundamental Problem It Solves

In traditional automation workflows, each workflow node directly calls a specific AI provider API (e.g., calling Google's API with a hardcoded Gemini key, or Alibaba's WanX API with a hardcoded DashScope key). This causes severe architectural friction:

  • Credential Sprawl: Sensitive API keys end up duplicated across dozens of n8n workflows, client apps, and configuration files.
  • Vendor Lock-in & Hardcoding: If a model is deprecated, or if we want to switch the writer role from Gemini to Qwen or Claude, an administrator must manually open, edit, and re-test 20+ individual workflow nodes.
  • Format Inconsistency: Google returns candidates in one structure, OpenAI in another, and Alibaba image models in another. Every workflow is forced to write brittle parsing logic.

How the AI Gateway Fixes This

With the AI Gateway, applications and workflows never talk directly to AI providers. Instead, workflows ask the Gateway for a Role (e.g., "I need the Writer" or "I need the Image Generator").

Figure 1.1: Core concept of Role-Based Decoupled AI Gateway Orchestration
The Administrator's Superpower

Because routing is stored in the database, you can switch an entire content pipeline from Qwen-Max (Alibaba) to Gemini-1.5-Pro (Google) by changing a single row in the ai_roles database table. Zero workflows need to be edited, tested, or redeployed.

03 Complete Request Lifecycle

When any application or n8n workflow issues a request to the AI Gateway, the request executes through a strictly sequenced 12-step lifecycle.

parseGenerateRequest() to extract role, mode ("template"|"direct"), and type ("text"|"image"). Step 4-6: Gateway reads ai_roles to find primary_model_id, then joins ai_models and ai_providers to get URL & secret name. Step 7-9: Secret is securely resolved via Deno.env.get(). Step 10-12: Adapter executes HTTP fetch to vendor, maps proprietary result into GatewayResponse, and returns clean JSON to caller.

04 Role / Model / Provider Model

The Gateway architecture is organized into three distinct, hierarchical layers:

Layer 1
ROLE (Logical Persona)

Represents what job needs to be done. Defined in table ai_roles. Examples: writer, planner, image_generator, rewrite, image_planner. Workflows only ever ask for a role.

Layer 2
MODEL (Specific AI Intelligence)

Represents the specific AI model version. Defined in table ai_models. Examples: gemini-1.5-pro, qwen3.8-max, qwen-image-2.0. Links to a parent provider.

Layer 3
PROVIDER (The AI Vendor)

Represents who hosts and serves the model. Defined in table ai_providers. Examples: google, alibaba-dashscope, alibaba. Holds the API base URL and secret variable name.

Database Relationship Hierarchy

ai_roles.primary_model_id ➔ references ai_models.id
ai_models.provider_id ➔ references ai_providers.id

06 Prompt Modes (TEMPLATE Mode vs. DIRECT Mode)

The AI Gateway supports two distinct operational prompt modes: TEMPLATE Mode (default) and DIRECT Mode.

{ role: "writer", variables: {...} } 2. Gateway reads ai_roles.active_prompt_template_id 3. Gateway fetches template from ai_prompt_templates 4. Interpolates variables into {{ placeholders }} 5. Passes compiled prompt to LLM Adapter Fails with 400 if active template is not configured in DB MODE: "direct" (Image Gen & Dynamic Custom Prompts) 1. Caller sends explicit prompt: { mode: "direct", userPrompt: "..." } 2. Gateway completely BYPASSES template lookup 3. Resolves model & provider strictly for routing & credentials 4. Passes userPrompt directly to Adapter 5. Ideal for complex multi-step prompt builders (WanX/DALL-E) No template configuration needed in database
Figure 6.1: Template Mode vs Direct Mode Logic Branching in Gateway
TypeScript Snippet from index.ts 
// Exact logic branching in supabase/functions/ai-gateway/index.ts
let finalSystemPrompt = parsedRequest.systemPrompt;
let finalUserPrompt = parsedRequest.userPrompt;

if (mode !== "direct") {
  // In TEMPLATE mode, resolve active template from database
  const template = await resolveActivePromptTemplate(req, roleData.id);
  if (!finalSystemPrompt) {
    finalSystemPrompt = renderTemplate(template.systemTemplate, variables);
  }
  if (template.userTemplate) {
    const renderedUserTemplate = renderTemplate(template.userTemplate, variables);
    finalUserPrompt = finalUserPrompt ? renderedUserTemplate + "\n\n" + finalUserPrompt : renderedUserTemplate;
  }
}
// In DIRECT mode, finalUserPrompt and finalSystemPrompt are passed straight to adapter!

07 Adapter Architecture & Factory

Adapters isolate the Gateway core from the proprietary APIs of different AI vendors. The Gateway core only calls standard methods defined in AIProviderAdapter (generate, generateStream, generateImage).

Registered Adapters

Adapter Name Handled Protocols / Providers Text Support Image Support Endpoint URL Construction
GoogleAdapter google / Gemini API Yes (JSON & Markdown) No ${baseUrl}/models/${model}:generateContent?key=${apiKey}
OpenAICompatibleAdapter openai-compatible, standard LLM endpoints Yes (Streaming & Sync) No ${baseUrl}/chat/completions with Bearer ${apiKey}
AlibabaAdapter alibaba / WanX Image Generation No Yes ${baseUrl}/services/aigc/multimodal-generation/generation

AdapterFactory Routing Logic

The AdapterFactory selects the appropriate adapter based on the provider slug and protocol:

TypeScript Snippet from adapters/factory/factory.ts 
export class AdapterFactory {
  static getAdapter(providerSlug: string, protocol?: string): AIProviderAdapter {
    // Alibaba image provider slug must be checked FIRST
    if (providerSlug.toLowerCase().startsWith("alibaba")) {
      return new AlibabaAdapter();
    }

    if (protocol === "openai-compatible") {
      return new OpenAICompatibleAdapter();
    }

    if (protocol === "google" || providerSlug.toLowerCase() === "google") {
      return new GoogleAdapter();
    }

    throw new Error(`Unsupported AI provider protocol: ${protocol || providerSlug}`);
  }
}
The Alibaba Special Case (Text vs Image Routing)

Alibaba Cloud DashScope provides two completely different API styles:
1. Text Models (Qwen): Use an OpenAI-compatible endpoint at .../compatible-mode/v1/chat/completions. In our database, this provider is registered as alibaba-dashscope with metadata {"protocol": "openai-compatible"}.
2. Image Models (WanX / Qwen-Image): Use Alibaba's native multimodal API at .../api/v1/services/aigc/multimodal-generation/generation. In our database, this provider is registered as alibaba and uses AlibabaAdapter.

08 Adding a New AI Provider

Follow this administrator guide to connect a new AI vendor to the Gateway.

Scenario A: Provider Uses an Existing Protocol (e.g. Any OpenAI-Compatible Provider like DeepSeek, Mistral, Groq, Perplexity)

No code changes or deployments are required! You only need to add the secret and insert a row in the database.

Step 1
Add API Key Secret

Add the secret to your environment.
NAS: Add GROQ_API_KEY=gsk_... to NAS .env.
Supabase: supabase secrets set GROQ_API_KEY=gsk_...

Step 2
Insert Database Provider

Run SQL in Supabase SQL Editor to register the provider with {"protocol": "openai-compatible"}.

Step 3
Insert Model & Link Role

Create model in ai_models and link your role in ai_roles. Immediate live execution!

SQL 
-- Example: Adding Groq as an OpenAI-compatible provider
INSERT INTO public.ai_providers (slug, name, api_base_url, secret_name, metadata)
VALUES (
  'groq',
  'Groq Cloud',
  'https://api.groq.com/openai/v1',
  'GROQ_API_KEY',
  '{"protocol": "openai-compatible"}'::jsonb
);

-- Register a model under this new provider
INSERT INTO public.ai_models (provider_id, model_name, display_name, context_window_tokens, max_output_tokens)
VALUES (
  (SELECT id FROM public.ai_providers WHERE slug = 'groq'),
  'llama-3.3-70b-versatile',
  'Llama 3.3 70B (Groq)',
  128000,
  8192
);

Scenario B: Provider Requires a Brand New Adapter (e.g. Anthropic Claude native API)

  1. Create supabase/functions/ai-gateway/adapters/anthropic/adapter.ts implementing AIProviderAdapter.
  2. Register the protocol in supabase/functions/ai-gateway/adapters/factory/factory.ts.
  3. Commit and deploy the updated Gateway to Supabase Edge and NAS Docker.
  4. Insert the provider and model records into the database.

10 Changing a Model for a Role

To switch which model powers a role, update the primary_model_id in ai_roles.

SQL 
-- Switch the 'writer' role to use Gemini 2.0 Flash
UPDATE public.ai_roles
SET primary_model_id = (
  SELECT id FROM public.ai_models WHERE model_name = 'gemini-2.0-flash'
)
WHERE role_slug = 'writer';
Zero Workflow Changes Required

The n8n workflow continues making the exact same call to role: "writer". The very next execution automatically runs against the new model!

11 Changing Model Providers

If you want to move a role across completely different providers (e.g. switching writer from Alibaba Qwen to Google Gemini):

  1. Verify that the destination provider's secret (e.g. GOOGLE_API_KEY) is configured in your NAS .env and Supabase Secrets.
  2. Ensure the destination model exists in ai_models.
  3. Update ai_roles.primary_model_id to point to that model.

12 Secrets & API Key Management

Security Rule: Raw API keys and secrets are NEVER stored in the database.

The ai_providers.secret_name column stores only the name of the environment variable (e.g. "DASHSCOPE_API_KEY"). At runtime, the Gateway executes Deno.env.get(secret_name) to retrieve the raw key securely from memory.

Managing Secrets in NAS Docker

Secrets are stored in the .env file in your NAS deployment folder (e.g. /volume1/docker/ai-gateway/.env):

20 Image Generation Flow

During standard article creation, image generation proceeds through the following pipeline:

  1. Image Planner AI (Gemma 4 31B): Analyzes article plan and generates structured anatomical yoga specifications.
  2. Image Prompt Builder: Compiles detailed photorealistic prompt text and negative prompts.
  3. Alibaba Image Generation HTTP: Sends mode: "direct", type: "image" request to AI Gateway.
  4. AI Gateway (AlibabaAdapter): Calls Alibaba WanX multimodal API, returns clean image URL in images[0].url.
  5. Cloudinary Upload: Downloads image and uploads to Cloudinary CDN folder yoga/general/article.
  6. Insert Image Asset: Stores record in table image_assets with version = 1, is_primary = true.

21 Image Regeneration Flow (Child Workflow)

When an administrator requests an image regeneration from the Admin Dashboard:

  1. Admin clicks "Regenerate Image" in Admin UI ➔ Triggers Webhook in Sub - Image Regeneration.json with image_asset_id.
  2. Get a row: Fetches the existing row from image_assets to retrieve the original prompt, negative prompt, and Cloudinary public ID.
  3. AI Gateway Request: Submits direct image request to AI Gateway using original prompt parameters.
  4. Download & Cloudinary: Uploads newly generated image to Cloudinary using versioned naming: {{ cloudinary_public_id }}-v{{ version + 1 }}.
  5. Create a row: Inserts a new row in image_assets with version: version + 1 and is_primary: false (preserving historical version 1 intact).
  6. Respond to Webhook: Returns success JSON to the Admin UI.

22 Debugging & Troubleshooting Guide

Error Message / Symptom Root Cause Resolution Steps
Active prompt template is not configured. (400) Image request sent in template mode instead of direct mode, or Gateway container is running old code that doesn't support mode: "direct". Ensure request payload has "mode": "direct". If payload has it, rebuild NAS container without cache (docker-compose build --no-cache).
OpenAI-compatible API Error (404): The provider's api_base_url has an incorrect path (e.g. missing /compatible-mode/v1 on Alibaba DashScope). Update ai_providers.api_base_url to https://ws-...maas.aliyuncs.com/compatible-mode/v1 for text Qwen models.
Provider secret not configured. (400) The environment variable specified in ai_providers.secret_name is missing from NAS .env or Supabase Secrets. Add the secret name (e.g. DASHSCOPE_API_KEY) to NAS .env or run supabase secrets set.
OpenAI-compatible API Error (401): invalid_api_key A workspace-specific key (sk-ws-...) is being sent to the global DashScope endpoint, or vice-versa. Ensure the provider's api_base_url matches the key scope (e.g. private ws-w18n... workspace).
Adapter ... does not support image generation (400) An image request was routed to a role whose model belongs to Google or a text-only OpenAI provider. Change ai_roles.primary_model_id for image_generator to point to an Alibaba image model (e.g. qwen-image-2.0).

25 Security Guidelines

  • Principle of Least Privilege: Never expose the service_role key to frontend clients. Frontend apps must only use the Supabase anon key with Row Level Security (RLS) policies.
  • Zero Raw Keys in Git: Never commit .env files or API keys to GitHub repositories.
  • Masked Logging: The Gateway automatically logs request metrics while keeping API keys and authorization headers masked.

26 Safe Change Management

  1. Database Changes: Always test model switches using a SQL transaction or testing with an unused test role first.
  2. NAS Container Rebuilds: Always keep a backup copy of your working .env file before rebuilding containers on the NAS.
  3. Edge Function Deployments: Test changes locally using supabase functions serve before deploying live to production.

27 Rollback Procedures

If a new model or adapter deployment fails in production:

  • Model/Provider Rollback: Revert ai_roles.primary_model_id in the Supabase SQL editor to the previous model ID. Effect is instantaneous.
  • Supabase Edge Function Rollback: Redeploy the previous Git commit using git checkout <previous-commit> && supabase functions deploy ai-gateway.
  • NAS Container Rollback: Revert local files on NAS and run docker-compose build --no-cache && docker-compose up -d.

29 Architecture Decision Record (ADR)

ADR 001: Decoupled Role-Based Gateway Architecture

Status: Approved & Implemented (August 2026)
Context: High maintenance overhead from hardcoding AI provider endpoints and API keys inside 20+ n8n workflow nodes.
Decision: Route all AI requests through a unified TypeScript Gateway. Store role-to-model and model-to-provider mappings in PostgreSQL. Support dual execution (NAS on-prem for internal speed, Supabase Edge for public webhooks).
Consequences: Zero-downtime model switching via SQL, centralized secret storage, standardized error handling and response normalization.
